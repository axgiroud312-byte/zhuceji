# ISS-010：执行指定数量任务并限制同一时间只运行一个网站

## 目标与范围

把资源绑定、网站脚本和任务数量组合为一次运行。数量表示任务数，不表示成功目标；失败记录原因，不自动新增替代任务。同一时间只允许一个网站运行。

## 必要设计与依据

- 调查 `scheduler.py`、`lock.py`、`storage.py` 及 `web.py` 的批次控制，复用状态持久化与运行锁。
- 启动时固定脚本版本、资源绑定和数量；参数非法、资源不满足或脚本不可用应在启动前说明原因。
- 服务端保证互斥和重复启动防护，不能仅禁用前端按钮。双标签页、重复请求和不同批次不得绕过限制。
- 界面明确区分任务总数、成功、失败、运行中、待执行，不显示追赶成功目标的补跑进度。
- 核对现有自动重试：不得为失败任务隐式重新注册或创建替代任务。允许的传输层重试必须与注册提交区分；已提交结果未知时保留待核查状态，避免重复提交。
- 同站点并发、停止收尾和中断恢复尚属实施建议：调查后记录确定语义。建议停止后不启动新任务，进行中任务完成或超时后释放资源；退出和崩溃后不能留下永久运行锁，也不能擅自重新提交。

## 验收方法

输入 20，受控脚本中 3 个失败，最终仅有 20 个任务、17 成功、3 失败，不发生失败任务重新注册或补任务。运行 A 时通过 UI 和直接 API 启动 B 都被拒绝；重复点击不会重复创建批次。停止、异常退出及恢复后状态可解释且锁/租约正确释放，结果未知的已提交任务不会重新注册。

## 当前进展

- 开发与运行语义验证完成，待整体 PR 评审。负责人：Astra；分支 `feat/modern-web-workbench`；[整体 PR #1](https://github.com/axgiroud312-byte/zhuceji/pull/1)。

- 实测 20 条 / 17 成功 / 3 失败且不补任务；直接 API/不同控制器/实际子进程互斥、停止收尾、OS 释放锁、中断恢复、提交标记中途故障均有验证。见 [状态规则](../状态规则.md) / [整体验收](../runtime-acceptance.md)。
